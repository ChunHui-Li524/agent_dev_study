1. 异步 vs 线程

Python 的异步和线程有什么区别？我的练习里该用哪个？
05_async_batch.py 是典型的 I/O 密集型（等 API 网络响应），用异步最合适。线程也能并发等网络，但开销更大，不适合成百上千个请求。
对比项异步 async/await线程 threading
本质单线程，协作式切换多线程，OS 调度
适合场景I/O 等待（HTTP、DB、文件）包装阻塞代码、无法改 async 的库
切换时机遇到 await 主动让出操作系统决定，不可控
开销很轻，可开成千上万个 task较重，线程太多会拖慢系统
CPU 密集计算不能真正并行（仍在单线程）CPython 有 GIL，CPU 密集也几乎不能并行

练习中的时间线

顺序执行（无 gather）

问 prompt ──3s──► 问 RAG ──3s──► 问 Agent ──3s──►
总计 ~9 秒

异步并发（你的写法）

问 prompt ──┐
问 RAG   ──┼── 同时等 ──►
问 Agent ──┘
总计 ~3 秒（取最慢的那个）
关键理解：异步解决的是「同时在等多条网络响应」，不是「在多核上并行算 CPU」。CPU 密集任务应使用 multiprocessing 或多进程。

2. 何时加 async / await

写异步代码时经常忘记加 async、await，怎么判断哪里该加？
记一条总规则：会等 I/O 且库提供异步版本的调用前面加 await；函数体内用了 await 的，定义时加 async def。
关键字什么时候加典型例子
async def 函数内部会写 await async def ask_question(...)
await 在等 async 函数、AsyncClient 方法、gather/sleep 等 await client.chat.completions.create(...)
asyncio.run 脚本入口，启动整个 async 程序 asyncio.run(batch_ask_questions())

调用链必须接好

asyncio.run(...) → async def batch_ask_questions → await gather(...) → await ask_question × N → await client.create(...)

常见报错对照

漏了什么报错 / 现象
该 async def 没加SyntaxError: 'await' outside async function
该 await 没加coroutine was never awaited 或得到 <coroutine object ...>
在 __main__ 里直接 awaitSyntaxError: 'await' outside async function
没 await 就取 .choicesAttributeError（response 其实是 coroutine）
练习代码对照：
  • def get_questions() — 普通函数，无 async/await
  • async def ask_question — 内部有 await create(...)
  • await asyncio.gather(*tasks) — gather 前面也要 await

3. 协程是什么

协程就是指 async 定义的函数吗？
方向对，但要更精确：async def 定义的是「协程函数」；调用它得到的是「协程对象」。日常说的「协程」多指后者。
概念含义例子
协程函数用 async def 定义async def ask_question(...):
协程对象调用协程函数后的返回值ask_question(client, q) 的返回值
Task被事件循环调度的协程对象asyncio.create_task(...)
 
async def ask_question(...):   # 协程函数
    ...

coro = ask_question(client, q)  # 协程对象，还没执行
print(coro)  # <coroutine object ask_question at 0x...>

result = await coro             # await 才驱动执行到结束

4. 调用 vs 执行

async def 定义的函数，如果只普通调用如 run()，只是创建对象，没有执行；await 或 gather 后才真正执行？
完全正确。注意：这里说的 run() 是自己定义的 async 函数，不是 asyncio.run()。asyncio.run(coro) 会创建对象并立即执行到结束。
写法是否执行函数体
ask_question(...)否 只创建协程对象
await ask_question(...)是
await asyncio.gather(...)是
asyncio.run(batch_ask_questions())是 程序入口专用
执行时机：协程被调度后从第一行开始跑；遇到第一个 await 时若还在等 I/O 就暂停，让出给其他协程；I/O 完成后从这里继续。

因此练习里三个「开始等待AI回答」几乎同时打印，是因为 gather 调度后，三个协程都跑到了 await client.chat.completions.create(...) 才开始等网络。

5. tasks 列表与 gather

tasks = [...] 时函数都没执行，直到下一行 await 才开始？gather 负责调度，await 触发 gather，然后等所有结果？
全部正确。事件循环是真正的调度者；gather 是工具，把多个协程绑在一起并发跑，等全部完成后按顺序返回 list。
tasks = [ask_question(async_client, q) for q in questions]  # 只创建对象
result = await asyncio.gather(*tasks)                  # 这里才真正开跑
第 1 步 — 列表推导式创建 coro1、coro2、coro3，函数体一行都不跑
第 2 步 — await gather 把三个协程交给事件循环并发调度
第 3 步 — 各自跑到 await create(...) 时开始等网络
第 4 步 — 全部完成后，gather 按 tasks 顺序返回 [(q1,a1), (q2,a2), (q3,a3)]
记忆：gather = 一起开工 + 一起等齐 + 按顺序打包结果。

6. create_task 的用法

create_task 是不是为了在 gather 之前就开始执行？
对。create_task 把协程包成 Task 并立刻挂到事件循环；在已有 loop 里，gather 之前就可能已经开工。

写法 A — 你的代码

tasks = [ask_question(...) for ...]
await asyncio.gather(*tasks)
# gather 之前：完全不执行
# gather 时：启动 + 等待 + 收结果

写法 B — create_task

tasks = [asyncio.create_task(ask_question(...)) for ...]
await asyncio.gather(*tasks)
# create_task 后：可能已在等 I/O
# gather 时：主要是等待 + 收结果
重要修正 — create_task 不是给 CPU 密集计算用的：

asyncio 跑在单线程事件循环里。I/O 等待时 await 会让出；CPU 密集计算会占满线程，堵住整个 loop，其他协程也动不了。CPU 重活应使用 multiprocessing 或 run_in_executor。

create_task 的真正价值：提前启动 I/O；中间插入轻量同步准备；并行多路 async 工作。

# create_task 典型用法：先飞请求，中间干别的事，再收结果
task = asyncio.create_task(ask_question(client, q1))
other_data = get_questions()   # 轻量同步准备
answer = await task              # 汇合

create_task 必须在已有事件循环的 async def 内使用；脚本顶层直接调用会 RuntimeError。

7. create_task 之后谁先执行

create_task 之后就会接受异步调度，后面的 other_data 会立马执行吗？
other_data 会立刻执行（同步代码）。但 ask_question 函数体通常要等到当前协程遇到 await 让出后，事件循环才会调度那个 Task。
task = asyncio.create_task(ask_question(client, q1))  # ① 登记 Task，马上返回
other_data = get_questions()                        # ② 同步，立刻执行
print(other_data)                                   # ③ 继续同步执行
answer = await task                                   # ④ 让出，等 Task 完成
时机发生什么
create_task 返回后Task 进入待运行队列；当前函数继续往下走
中间同步代码先跑完；ask_question 通常还没开始
await task让出控制权；事件循环跑 Task 或等其 I/O 结果
记忆：create_task = 先排队；同步代码 = 先跑自己的；await = 让出并等待。

8. PyQt GUI + 异步

开发 PyQt 桌面应用，Qt 本身有事件循环，想简单用异步是不是开线程在线程里跑 asyncio？
对，这是常见且正确的做法：主线程给 Qt，asyncio 放工作线程，结果用 pyqtSignal 回主线程更新 UI。
为什么不能主线程直接 asyncio.run？

PyQt 主线程已被 app.exec() 占用。同一线程两个事件循环难以共存；主线程 await 会卡死界面。

class AsyncWorker(QThread):
    finished = pyqtSignal(str)

    def run(self):
        result = asyncio.run(self._ask())  # 工作线程里跑 asyncio
        self.finished.emit(result)         # signal 回主线程

    async def _ask(self):
        # AsyncClient + gather 写在这里
        ...
规则原因
asyncio.run 放在 QThread.run()该线程有自己的 asyncio 事件循环
用 pyqtSignal 回主线程Qt 控件只能在主线程修改
不在 worker 里直接 label.setText会不稳定或报错

9. 100 个并发 — 谁先完成谁先显示

100 个 AI 请求，希望哪个结束就立马显示，是不是该用线程发信号，而不是异步？
异步仍然很合适。不合适的是「只用 gather 等全部完成再统一显示」，不是 asyncio 本身。不必开 100 个线程。

方案对比

方案评价
100 个 QThread不推荐 开销大、难管理
1 个 QThread + asyncio 并发 100 路 I/O推荐
线程池 + 同步 API（如 max_workers=20）可以 简单但并发受池大小限制
主线程同步调 API不行 界面卡死

两种「逐个显示」写法

写法 1：每个任务完成时内部 emit（gather 仍可留作「全部结束」收尾）

async def ask_one(self, question):
    answer = await self.client.chat.completions.create(...)
    self.result_ready.emit(question, answer)  # 完成就立刻发
    return question, answer

tasks = [asyncio.create_task(self.ask_one(q)) for q in questions]
await asyncio.gather(*tasks)  # 只等最后一个；中间 signal 早已发出
self.all_finished.emit()

写法 2（更直观）：as_completed 按完成顺序处理

for done in asyncio.as_completed(tasks):
    question, answer = await done
    self.result_ready.emit(question, answer)
self.all_finished.emit()

10. as_completed 详解

as_completed 返回的是什么？循环和循环体里的 await 分别等什么？
返回普通同步迭代器，每次 yield 一个 awaitable（「下一个刚完成的那一项」）。for 每次取一个；循环体内 await 取出该任务的真实返回值。

两层含义

步骤代码等什么
① for 迭代 for done in as_completed(tasks) 等「下一个完成的任务」出现
② 循环体内 result = await done 取出已完成任务的返回值（通常瞬间完成）

时间线示例（耗时 3s / 1s / 2s）

t=0s — 三个请求并发发出
t=1s — q2 最先完成 → 第一次循环 → 打印 q2
t=2s — q3 完成 → 第二次循环 → 打印 q3
t=3s — q1 完成 → 第三次循环 → 打印 q1

打印顺序：q2 → q3 → q1（按完成时间，不是提问顺序）。

与 gather 对比

gatheras_completed
返回时机全部完成后才返回 list每完成一个 yield 一个
顺序与传入顺序一致按完成先后
适合批量收齐再处理完成一个处理一个（如实时刷 UI）

11. 普通 for 还是 async for？

你之前写了 async for，又说普通 for，到底哪个正确？
标准写法是普通 for + 循环体内 await。as_completed 返回的是同步迭代器，不支持 async for。

正确

for done in asyncio.as_completed(tasks):
    result = await done

错误

async for done in asyncio.as_completed(tasks):
    result = await done
# TypeError：没有 __aiter__
整个 for ... await 块必须写在 async def 函数里，因为循环体含有 await。

12. 速查清单

写代码时扫一眼

  1. 函数里有 await？→ 声明必须是 async def
  2. 等网络 / AsyncClient / gather / sleep？→ 前面加 await
  3. 调用自己的 async def？→ 调用处要 await（或放进 gather）
  4. 脚本入口？→ asyncio.run(main())，不要顶层 await
  5. 看到 <coroutine object ...>？→ 少写了 await

场景选型

场景推荐
多个 HTTP / API 并发等async + gather 或 as_completed
完成一个显示一个（PyQt）QThread + asyncio + as_completed + signal
gather 前想先干别的事create_task
现成同步库、无法改 async线程池
CPU 密集计算multiprocessing / run_in_executor
PyQt 主线程只跑 Qt；asyncio 放工作线程

一句话总纲

  • 造对象 vs 跑对象：普通调用只造协程对象；await / gather / asyncio.run 才是跑对象
  • asyncio 擅长：同时等多件 I/O 的事
  • CPU 算力：交给进程或线程池，别堵事件循环
  • as_completed：外圈 for 等「谁刚完成」，内圈 await 拿结果；用普通 for
